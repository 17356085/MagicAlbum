## Feed 评估方法

隔离演练使用实际 Flyway 迁移、MySQL 8 和当前 Spring Data 查询，分别记录系统现有投影及总数的耗时，以及等价过滤条件的分页、计数耗时和执行计划。固定数据下核验同一创建时间的顺序，并用上一页最后一项作为游标，在同一个深页比对有序 ID。插入新主题后验证页码偏移能否造成重复，再对照游标行为。隐藏、删除和取消关注分别做数据库读回。

报告记录合成数据规模和数据库镜像。仓储时间包含查询结果投影和计数，原型记录已有游标时的页面 SQL。每种场景预热两次并测量八次，记录分位数用于复验。该演练采用串行读、热缓存及合成内容，回复和点赞表没有负载，无法据此推算生产容量或峰值服务量。

## Feed 测量与决策

本地预演使用 MySQL 8.0.46，写入 128 名作者的 20,480 条主题，其中 128 条隐藏、128 条删除。每页 20 条，结果为八次测量的 p50 和 p95，单位毫秒。

| 场景 | 可见主题 | 现有仓储分页与计数 | 等价分页 SQL | 等价计数 SQL | 已有游标时的页面 SQL |
| --- | ---: | ---: | ---: | ---: | ---: |
| 关注 8 人，第 1 页 | 1,264 | 13.47 / 17.55 | 2.14 / 2.57 | 1.72 / 2.42 | — |
| 关注 128 人，第 501 页 | 20,224 | 53.75 / 59.65 | 23.75 / 28.01 | 15.77 / 17.58 | 16.13 / 19.60 |

首页的过滤计划从关注关系索引开始，宽关注深页计划从主题状态索引开始。两种深页 SQL 在数据不变时返回相同的已排序 ID。插入新主题后，现有页码分页重复返回 1 条，游标原型避免了重复，且再次查询时排除了隐藏、删除和取消关注的内容。

初次 ARCH-15 评审决定保留 Core 查询、页码跳转和现有部署边界。独立投影需要额外完成回填、幂等、治理与关系权限更新、数据对账和回退。试验已验证分页优化方向，尚无线上负载证据表明需要新增独立 Feed 存储或服务。

## 关注流相邻翻页

关注流页面选用 `GET /api/v1/threads/following?pagination=cursor`。首页聚合和原有客户端继续使用同一路径下的页码接口。游标模式沿用 `items`、`page`、`size` 和 `total`，另返回 `nextCursor` 与 `previousCursor`，没有相邻窗口时对应字段为 `null`。

| 操作 | 请求与结果 |
| --- | --- |
| 打开或刷新页面 | 从第 1 页开始读取当前关注流 |
| 点击下一页 | 发送 `after`，按创建时间和主题 ID 读取当前末项之后的较旧内容 |
| 点击上一页 | 发送 `before`，按同一排序读当前首项之前最近的较新内容 |
| 输入页码 | 按当前列表定位该页，生成新的相邻游标 |
| 重试相邻翻页 | 在账号和频道仍相同的情况下使用刚才的游标 |
| 切换到某位作者 | 使用该作者原有的页码接口 |

每次读取都以当前账号的关注关系和正常状态主题为准。新帖出现在现有首项之前时，顺序翻下一页不会再次返回上一页的末项。内容隐藏、删除或取消关注会影响已打开页面的后续查询。页码在游标请求中用来显示当前位置，总数来自本次查询，列表的变化仍可能改变可跳转页数。

游标是带版本和账号标识的分页位置。服务端用当前会话和数据库重新判断可见性。格式无效、账号不匹配或同时传 `before` 与 `after` 时返回 HTTP 400，未登录时返回 HTTP 401。前端识别只返回旧页码格式的旧版本，继续提供页码翻页。

MySQL 专项复用 20,480 条主题的隔离夹具，对真正在 Core 中执行的游标读取检查相邻行、直接跳转、账号隔离和内容可见性。浏览器验收随默认与分库拓扑运行。[MySQL 验收](../../scripts/ci/feed-query-cost.py) · [浏览器验收](../../tests/e2e/playwright/test_m0_journey.py)

## 服务提取与基础设施评审

| 审计项 | 决策门槛 | 下一次评审需要的证据 |
| --- | --- | --- |
| ARCH-15 Feed | 深页成本、关注扇出或数据库争用影响实际产品目标时，才为 Feed 增加独立存储和异步同步 | 实际流量的查询时延和数据库争用，独立投影的写入放大、回填时间及权限更新时延 |
| ARCH-16 Social | 服务发布可以独立，且关注、好友、拉黑与联系授权能够通过明确的所有者契约提供 | 分离后 Feed 查询能维持现有可见性，联系授权维持现有并发语义，端到端对比能显示部署或规模收益 |
| ARCH-16 Search | 搜索资源或恢复时间有独立扩缩容的需要 | Elasticsearch 投影、搜索回源和写入负载的分段指标，切换和回退对账 |
| ARCH-16 Content | 权威写入需要独立发布或扩容，且治理、通知和搜索消费者能承受独立故障 | 真实写入峰值、连接池占用和恢复时间，对应事务与 Outbox 证据 |
| ARCH-18 Kubernetes 和 Service Mesh | 运维环境确实需要多主机调度或统一服务间治理 | 跨主机恢复、滚动升级和故障复现，现有 Compose 基线的成本对照 |
| ARCH-18 Rust | 可复现热点和 Go、Java 基线显示需要独立组件 | 相同吞吐、延迟和资源指标，加上维护成本和回滚验收 |

当前保留 Core、网关、通知、Go 实时接入、Go 媒体 worker，以及可单独构建的聊天应用。ARCH-16 本轮暂缓提取 Social、Search 和 Content。Social 的关系状态与 Feed 仍共享 Core 事务和数据，搜索索引已有独立的 Elasticsearch 投影与回放入口，Content 仍负责帖子及治理更新并通过 Outbox 发布。本轮证据覆盖了这些边界的运行与恢复，未提供额外拆分可以降低业务负载或发布成本的实测。

ARCH-18 暂缓 Kubernetes、Service Mesh 和 Rust。基础 Compose 包含 8 个服务和 4 个命名卷，分库覆盖层增至 10 个服务和 5 个卷。日志、搜索和媒体按需启用。换用多主机调度至少会增加这两套拓扑的发布、持久存储恢复和回退验证，还需单独验证内部身份、网关路由与健康检查。现有 Compose 已通过双拓扑、迁移、回滚与恢复演练。Java 和 Go 的同负载实验记录了 WebSocket 鉴权的吞吐、延迟和资源，但没有定位到需要新语言的热点，也没有生产指标显示多主机调度或统一代理治理的需求。保留按上表重新评审的验收门槛。[总体架构](01-总体架构设计.md) · [聊天构建与契约](12-M7-service-build-and-contracts.md) · [Kafka 与数据库验收](13-M8-data-and-event-pilots.md)
