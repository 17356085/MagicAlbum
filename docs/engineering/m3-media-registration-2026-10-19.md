# M3.2 首批：上传意图与媒体登记

日期：2026-10-19。状态：本地实现；M3 整体尚未完成，默认不开启异步登记。此记录与 M2 已推送的验收结果分开。

## 本批范围

Java 核心仍是媒体数据所有者。新增三个 storage 域内模型：`media_asset` 保存资源归属和原始对象信息，`media_processing_job` 保存第一版 preview 任务，`media_request_outbox` 保存待投递请求。新增迁移 `V20261019_3__media_registry.sql`，不依赖用户/帖子 Entity 或 Repository。

本批不是完整 worker：代码目前仅创建 `PENDING` 任务和请求，没有实现执行中或成功状态迁移；发布租约、broker 确认、Go 消费、输入读取能力、结果接受及恢复清理均待后续实现。表约束预留了后续状态，但不代表生命周期已实现；下一批追加租约及结果字段迁移，不直接修改已发布迁移。

## 上传与事务

`MEDIA_REGISTRATION_ENABLED=false` 为默认值，原接口继续 `200 + {url}`。显式开启后仍同步保存原图，并增量返回 `assetId`、`jobId`、`processingStatus`，前端现有读取 `url` 的调用兼容。

1. provider 校验图片并准备随机对象键、稳定 URL、实际字节数和 SHA-256，此时不写存储。
2. `begin` 单独提交 `UPLOADING` 意图，保存之后要写入的精确位置。
3. 同一个已选择的 provider 写入原始字节。
4. `ready` 锁定资源，在一个事务里保存 `READY`、JPEG/PNG preview 任务和请求 Outbox；重复或并发确认只生成一个任务和事件。

GIF/WebP 的上传兼容现有 ImageIO 解码器能力，成功保存后不创建 Go 处理任务，处理状态为 `UNSUPPORTED`。本批没有添加 WebP 解码依赖。PNG 中的 APNG 尚未在 Java 侧分类；Go 内核将其拒绝，后续失败处理必须保留原图。

对象写入失败尝试将意图记为 `UPLOAD_FAILED`；这个状态不证明外部对象不存在。成功写入后数据库提交失败或响应不确定时保留意图，不立即删除文件。崩溃遗留的 `UPLOADING` 和失败记录可定位 provider/key，但自动对账、重试和孤立对象清理尚未实现，暂不在生产打开此功能。

## 校验和访问边界

上传不再信任 multipart 声明大小或调用无界 `getBytes`，读取实际字节最多 10 MiB。真实图片格式须与 MIME/扩展名对应，JPEG 的 jpg/jpeg 为兼容别名。ImageReader 先读取尺寸，限制单边 20000、总像素 2400 万后才完整解码，完整尺寸必须与头信息一致。错误不包含底层文件路径或解码器内部信息。

本地 provider 检查配置前缀和对象键，准备阶段不创建文件；写入在配置目录下逐层创建目录并拒绝已有符号链接目录，文件使用 `CREATE_NEW` 防覆盖。这不承诺抵御具有本机目录修改权限的攻击者并发替换目录。S3 使用准备阶段的精确随机键和字节；稳定读取 URL 及已有 CDN 配置保持兼容。

`GET /api/v1/uploads/assets/{assetId}` 使用登录用户查询归属；其他用户和未知资源返回相同 404。响应仅含资源 ID、URL、资源/任务状态及任务 ID，不暴露存储键、owner、SHA 或凭据。现有 `/uploads/**` 仍公开读取；这不是私有图库改造。
