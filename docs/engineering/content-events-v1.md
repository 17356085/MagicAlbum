# M2 内容事件 v1 契约

状态：M1 工程交接契约已冻结；M2 按下文分批实现。它描述目标语义，不代表 RabbitMQ 内容队列或 Elasticsearch 已上线。既有通知 Outbox 和 AI 摘要队列继续独立运行。

## 数据与事务归属

核心 content 域拥有帖子、评论、分区、标签及可见性。首批仅对帖子创建、编辑（含标签/分区）、隐藏和软删除记录事件；点赞、浏览、摘要状态不会推进正文版本。`ThreadService` 继续负责作者权限、状态检查和行锁；审核通过内容 owner 的隐藏命令操作。

帖子修改、`threads.content_version` 增量和 `content_event_outbox` 插入必须在**同一个数据库事务**内提交；Outbox 插入失败必须回滚业务修改，不得 catch 后继续成功。事务提交后直接发消息不能替代持久化 Outbox。后续发布器才将已提交记录交给 RabbitMQ。

版本为每个帖子单调递增的非负整数。已有数据迁移后为 0，第一次变更为 1；新建帖子第一个事件为 1。更新、隐藏、删除沿用 owner 的悲观写锁，防止两个事件取得同一版本。重复删除已删除帖子不产生新事件。现有软删除不物理移除帖子 ID，ID 不重新使用。

## 消息结构

```json
{
  "eventId": "2f630790-03be-4fb9-91a9-f1caad57de18",
  "schemaVersion": 1,
  "aggregateType": "THREAD",
  "aggregateId": 74,
  "aggregateVersion": 3,
  "eventType": "THREAD_HIDDEN",
  "occurredAt": "2026-10-18T15:00:00Z",
  "requestId": "request-id-or-null"
}
```

`eventId` 是持久化后重试不变的 UUID；`aggregateId + aggregateVersion` 在表中唯一。`schemaVersion` 与内容版本不同：前者表示协议兼容性，后者只表示一个帖子的变更顺序。`requestId` 仅用于诊断，按请求关联格式校验、最多 128 字符；它不是身份凭证。

消息只包含标识和状态变化，不携带正文、用户名、手机号、邮箱、令牌或图片凭据。消费者必须通过 content owner 的投影接口读取当前数据，不读取外域 Repository 或写业务表。索引查询结果仍须回到 owner 进行当前可见性检查，不能因索引命中就返回已隐藏内容。

| eventType | 含义 | 消费结果 |
| --- | --- | --- |
| THREAD_UPSERTED | 创建或编辑了当前 NORMAL 帖子 | 从 owner 取得当前投影；若已不可见，按当前版本生成不可见标记 |
| THREAD_HIDDEN | 审核隐藏 | 保存不可见墓碑及版本，清除可检索正文 |
| THREAD_DELETED | 作者软删除 | 保存不可见墓碑及版本，清除可检索正文 |

恢复可见性的 API 尚未实现；将来必须通过 owner 新命令推进版本并生成 UPSERTED，不能绕过事件直接修改状态。

## 投递、重放与错误

投递语义为至少一次。发布器必须确认 RabbitMQ 接收且消息可路由后再标记已发布；崩溃窗口可能造成重复。消费者完成派生索引持久化后才确认消费；不能把 publisher confirm 当作业务完成。[RabbitMQ 可靠性说明](https://www.rabbitmq.com/docs/reliability)、[确认机制](https://www.rabbitmq.com/docs/confirms)。

幂等与顺序由 `aggregateVersion` 判断，不由时间戳、消息到达顺序或 `redelivered` 标志判断。低于已应用版本的事件丢弃；相同事件/相同版本重放不改结果；相同版本但冲突的事件类型或 eventId 应告警隔离，不覆盖已有结果。消费者拉取到更高版本的 owner 投影时，以投影版本为准，避免给新数据贴上旧版本。

未知 schemaVersion、非法 ID/版本、冲突数据进入可诊断的失败状态；暂时不可用采用有界重试与退避，禁止无限热循环。只记录 ID、版本、错误类别、时长和状态，不能把正文或上游异常原文写入日志。

不可见版本标记必须跨重放长期有效。不能只删除 Elasticsearch 文档并假定旧事件永远不会重建正文：删除后的版本保留受 `index.gc_deletes` 限制。索引保留不含正文的墓碑/版本检查点，查询显式排除不可见标记。[Elasticsearch 删除 API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-delete)。

## 索引重建与故障回退

MySQL 是权威数据，索引为可重建派生数据。重建使用新索引：记录可靠的增量水位，按主键游标读取 owner 投影（包含不可见标记与版本），再重放水位之后的事件；并发扫描与重放也按版本比较。比对数量、抽样内容、隐藏/删除和版本后才切换别名，旧索引保留一个回退窗口。

**不能把在线查询到的 `MAX(outbox.id)` 直接当成可靠提交水位。** 自增 ID 分配顺序不是事务提交顺序：较小 ID 的在途事务可能在基线扫描之后才提交，从而同时漏过扫描和“只重放更大 ID”的增量。首版可采用明确的写入隔离窗口：暂停所有产生内容事件的 owner 写入，等待这些在途事务结束，记录水位并开启可靠增量捕获后再恢复写入；多实例必须全部参与。若不提供该隔离窗口，必须另行实现能覆盖晚提交的提交位置或持久化增量捕获方案，并验证“低 ID 晚提交”场景后才能切换索引。此处冻结的是正确性要求，尚未实现重建工具。

现有 LIKE 搜索保留为默认路径。新索引未就绪、超时或故障时回退数据库查询，保留分页与过滤契约；不得把依赖故障伪装成“无结果”。回退也必须由权威状态过滤。重建和别名切换失败时维持旧路径，禁止双份权威业务写入。
