我已详细分析了现有的代码结构和数据库设计。鉴于系统中 `Thread` 和 `Post` 表均已包含 `status` 字段（支持软删除），且数据库已配置物理级联删除约束，我建议采用 **级联软删除** 方案。这既能满足你"清理关联数据"的需求，又能保持数据可恢复性，符合现有架构风格。

以下是具体的实施计划：

## 1. 后端部分 (End)

### 修改 `PostRepository`
- **目标**: 提供批量更新评论状态的能力。
- **操作**: 在 `com.example.demo.posts.repo.PostRepository` 中添加一个自定义 JPQL 方法，用于将指定帖子下的所有评论状态更新为 `DELETED`。这比循环查询再保存性能更高。

### 修改 `ThreadService`
- **目标**: 实现事务性的级联删除逻辑。
- **操作**:
    1. 注入 `PostRepository`。
    2. 在 `delete` 方法上添加 `@Transactional` 注解，确保原子性。
    3. **逻辑流**:
        - 校验权限（仅作者可删）。
        - 调用 `postRepository.softDeleteByThreadId(threadId)` 标记所有关联评论为已删除。
        - 将帖子本身状态设为 `DELETED` 并保存。

## 2. 前端部分 (Front)

### 扩展 API 模块
- **文件**: `front/src/api/threads.js`
- **操作**: 添加 `deleteThread(id)` 函数，发送 `DELETE /api/v1/threads/{id}` 请求。

### 更新 UI 组件
- **文件**: `front/src/pages/MyThreads.vue` (或 `ThreadDetail.vue`)
- **操作**:
    - 在列表项中添加“删除”按钮。
    - 添加点击事件处理：弹出确认框 -> 调用 API -> 成功后从前端列表中移除该项（避免重新刷新页面）。

## 3. 验证与测试
- **验证点**:
    - 删除帖子后，数据库中该帖子的 `status` 变更为 `DELETED`。
    - 该帖子关联的 `posts` 表记录的 `status` 也变更为 `DELETED`。
    - 物理记录依然存在（符合软删除设计）。
    - 前端列表即时更新，不再显示该帖。
